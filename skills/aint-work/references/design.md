# 设计：功能、状态、面板、命令与素材

## 1. 需求 → 原语

先问作品需要什么体验，再选最少的原语实现它。

| 需求 | 做法 |
| --- | --- |
| 世界观、人物、地点 | `lore/` 设定文档；核心设定 `load: always`，其余 `index` |
| 有主线的长篇 | 主线拆成 `lore/outline/` 下按阶段的文档（`kind: outline`），`summary` 写阅读时机；执笔指令说明主线在哪、偏离时怎样回应 |
| 悬疑、推理、揭示 | 真相与揭示梯子常驻，细节按阶段读取；见第 4 节 |
| 开放漫游 | 执笔指令写世界的气质与可能的方向，设定提供素材，不写主线 |
| 玩家自定义角色 | `state.yaml` 声明字段 + `new_game.fields`；执笔指令与开场用 `{{ state.… }}` 引用 |
| 数值与资源（时间、金钱、体力、关系、物品） | `state.yaml` + 面板；`desc` 写清范围与更新时机 |
| 运气与检定 | `features.dice`；执笔指令写什么时候掷、骰子与结果的含义 |
| 特殊语义的陈述（判决、契约、系统宣告） | 样式标签 + 状态列表记录 + 面板展示 + 执笔指令说明效力 |
| 特殊输入（推理、祈愿、咏唱） | `present: [mode]` 命令 + `mode_style` 样式标签 |
| 多视角、切换跟随对象、偶尔看看别处 | 命令 + 执笔指令约定视线的边界；持续的跟随才加状态字段；见第 5 节 |
| 读者模式（玩家不扮演角色） | 执笔指令说明读者身份与干预方式；用命令表达干预；执笔者可以写全部人物的言行 |
| 多个起点 / 路线 | 多个开场，各自 `initial_state` |
| 场景演出 | 背景图（`role: background`）+ `<scene>`；插图 + `<cg>`；音频 + `<bgm>`/`<sfx>` |
| 图片线索、人物形象 | 素材 + 设定文档 `images`；每回合都要看见的才 `pin` |
| 纯选项推进 | `features.free_input: false`，执笔者每回合给出选项 |
| 长篇记忆 | 平台默认就有；有特别需要记的东西才写 `prompts/memory.md` |

很多作品只需要 `work.yaml`、执笔指令、开场与几份设定。

## 2. 状态

状态是面板的数据来源，也是执笔者保持前后一致的结构化记录。

- 少而精：只放玩家需要看到、或会影响执笔者判断的内容。叙事性的认知、关系细节、伏笔交给记忆，状态放数值、列表与一句话的局势。
- `desc` 写清含义、范围与单位、什么时候更新、显示在哪里。执笔者完全依靠它维护状态。
- 类型：一组人物各自的数值用 `map`（键为人物名）；物品与线索用 `list`；局势、地点用 `string`；成组的属性用 `object`。
- 开局表单要写入的字段放在顶层或 `object` 中。文本字段给一个合适的 `default`，玩家可以直接开始，预览也能看到效果。故事需要分开使用的部分（例如称呼要用到姓）拆成独立字段。
- 列表的长度按故事需要来定，不必为了面板显示而让执笔者压缩或合并条目；显示多少由面板模板决定（第 3 节）。

## 3. 面板

面板保持轻量：每一项一行，内容少，照顾手机上的玩家。

- 先想清楚玩家最需要一眼看到什么，只放这些。正文已经写到的东西不必在面板里重复。
- 顶栏（`topbar`）至多一个面板，输出一句短话（局势、日期、地点、一两个关键数值），用 `·` 连接。它显示在一条单行胶囊里，超出部分截断；多个顶栏面板会挤进同一条胶囊。
- 侧栏、抽屉每项一行：`<ui-stat>` 显示数值，`<ui-bar>` 显示进度，一个面板一个主题，不做多层标题的仪表盘。
- 累积的列表（线索、日志、物品）每条一行、写得短。条目多时可以只显示最近几条，新的在前：`{% for c in state.<list> reversed limit: 8 %}`；也可以放在抽屉里整份显示，抽屉内容可以滚动。
- 窄屏上侧栏面板成为底部抽屉的标签页；`float` 在手机上不显示，只放宽屏上锦上添花的东西，不能是唯一的信息来源。
- 用 `if` 让没有内容的面板自动隐藏；用 `{%-` / `-%}` 去掉多余的空白与换行，单行面板的输出保持一行：

  ```liquid
  {%- if state.<字段> != "" -%}{{ state.<字段> }}{%- endif -%}
  ```

## 4. 悬疑与揭示

执笔者需要始终知道真相，线索才会前后一致；玩家一层一层接近它。

- 不变的真相（谁、为什么、怎么做、关键的时间线）与揭示梯子（每一层在什么阶段、经由什么样的发现出现）写成一份简短的文档，`load: always`。它只放骨架，篇幅控制在一两千字以内。
- 证词、物证、场面等细节按阶段拆进 `index` 文档（如 `lore/outline/`），`summary` 写清什么时候读。
- 误导线索写明它实际指向什么、在什么时候被排除。
- 执笔指令坚决地约定揭示的方式：真相经由玩家角色自己的观察、追问与推理出现，旁白与其他人物不替玩家说破；梯子上还没到的一层，正文里只留痕迹。这是这类作品的核心机关，值得用坚决的语气说一次。
- 在 `prompts/memory.md` 里请执笔者记下每一层已经揭示到哪里、经由谁、在哪一回合；在 `prompts/compaction.md` 里请整理时保留揭示进度。

## 5. 命令与视角切换

- 大多数行动用自由输入或选项就够了。命令适合反复使用、需要固定格式的元操作：切换视角、读者干预、特殊输入模式、需要确认的终局操作。
- 命令少而精，每条都在 `description` 里写清它在故事中带来什么。
- 模板写成叙述层面已经成立的事实与下一段的起点，并在执笔指令中约定命令带来的变化直接体现在正文里（见 [写作](writing.md) 第 10 节）。
- 参数有固定的可选值时用 `options`；自由文字用 `{{ input }}`，不必设必填参数。
- 需要改状态时，在模板里写明更新哪个字段、改成什么。
- 只想给玩家用、不希望执笔者在选项或可点击词里主动提供的命令，设 `ai_visible: false`。

视角切换分两种：

- **持续的跟随**（此后一直从某人的视角讲）：状态里记当前跟随的人物，面板可以显示它；执笔指令写清怎样换回来。玩家进入或退出这种模式的途径不止命令，还有选项与自由输入，所以更新规则写在状态的 `desc` 与执笔指令里，覆盖每一种途径（"无论经由命令、选项还是玩家自己的话"）；命令模板里的那句更新只是其中一条途径的提醒。退出的条件同样写成意思（玩家叫回、转去做别的事）。
- **偶尔看一眼**（这一段看看别处，看完回来）：不需要状态字段。模板只说这一段跟随谁；执笔指令写清这一段从哪里接起（时间只往前走，人物还在一处时从分开之后写起）、怎样回到玩家角色（场景分隔与眼前的新景物），以及之后的选项仍属于玩家角色。

跟到藏着秘密的人物身上时，在执笔指令里写清视线能看到什么：他做了什么、见了谁、独处时的样子；他的秘密按揭示梯子放出，没到的那一层，视线走过去也只看见表面。这条边界值得用坚决的语气说一次。

## 6. 选项

- 平台让执笔者在一段叙事告一段落时给出 2–4 个选项。作品可以在执笔指令里写选项的气质，或约定固定的数量。
- 选项的 `command` 是可选的：只有选中后需要执行作品命令（例如切换跟随的人物）时才用。普通行动选项只有文字。静态开场的初始选项同样可以带 `command`。
- 选项的 `style` 取作品的样式标签，只用在少数有特殊含义的选项上。
- 以选项推进为主的作品，建议询问用户是否开启 `force_choices`。
- 限时选项（`timed_choices`）用在真正紧迫的情境，执笔指令里写清什么算紧迫。

## 7. 样式标签与文字特效

模型对标记语言的权重很高：给了标签，它会积极地用；写在标签里的文字，也容易变得死板、模板化。所以：

- 只用在本身固定、不需要文笔的内容上：判决与裁定、系统提示、技能与咒语的名字、规则性的宣告、纸面原文、少数特殊演出。
- 需要文笔的东西（容貌、情绪、氛围、亲密、动作、景物）始终留在正文里，用文字本身的功夫完成。用标签"突出"这些描写，会把它们变成格式化的片段，适得其反。
- 每个标签的 `description` 写清唯一的使用场合与频率，执笔者在其余时候自然不会用到它。
- 一部作品的样式标签通常是零到两三个。`presentation.text_effects` 默认关闭；开启时同样在执笔指令中限定场合。

## 8. 说话人样式

`presentation.dialogue` 默认 `plain`。`tagged` 要求执笔者把台词都写进 `<say who>`，对白随之固定成一种写法，与灵活多变的现代文文风、多样的"某人在说话"的表达方式冲突。只有用户明确要视觉小说式的说话人名字与颜色时才开启，并为人物文档写 `display.color`。

## 9. 主题与素材

主题可选。用户给了审美参考、或作品有鲜明的色调时再写：

- 配色从参考图或作品的意象中取，light 与 dark 两套都给，保证正文与背景的对比度。
- 背景图透明度低（约 0.05–0.15），正文始终清楚可读。
- 中文作品 `indent: 2em`；外语作品通常 `0`。
- 字体用 `serif` / `sans` 即可；自带字体需要子集化并确认许可。
- `custom.css` 只做主题表达不了的细节。

用户提供的图片，先分清用途。用户没说明时按审美参考处理；适合放进作品的，在对齐时提一句。

- **审美参考**：把配色、氛围、质感、人物气质转写进执笔指令、设定与主题，不必放进作品。
- **作品素材**：复制到 `assets/`（小写 ASCII 文件名），在 `assets.yaml` 写 `id`、`role` 与 `description`。
  - `role` 只有 `background` 有特殊作用：场景图标 `background`，执笔者用 `<scene bg>` 切换。其余图片的 `cg`、`avatar`、`reference` 效果相同，都可用于 `<cg>` 与 read。
  - `description` 写画面里有什么、适合什么时候用；使用的频率与时机写进执笔指令，不写使用记录。
  - 人物图关联到人物文档的 `images`；外貌特征同时写进人物文档正文，模型不能看图时也能写准。
  - 每回合都需要看到的图才 `pin: true`，通常不超过两三张；需要执笔者看图时写 `requires.vision: preferred`。
  - 封面写在 `work.yaml` 的 `cover`，书架上按 5:7 竖版居中裁切；比例不合适时不设封面，书架显示按标题生成的封面。
  - 封面与主题背景图只给界面用，不进入执笔者的素材索引。同一张图既做主题背景、又要做 `<scene>` 背景或插图时，复制成两个文件，各自引用。
- 图片长边 ≤ 2048 px，背景图用 webp；有图像工具时转换与缩放，没有时保留原图并告诉用户。
- 只出现在对话中、没有文件路径的图片放不进作品，只作审美参考；需要放进作品时请用户提供文件。
- 音频的 `description` 写清情绪与适用场景，执笔者据此决定何时换乐、何时放音效。

## 10. 记忆

平台默认让执笔者维护 `/memory`（索引、章节纪要、人物、伏笔、游玩中确立的设定、玩家偏好）。

- 作品有特别需要记的东西或特别的组织方式时，才写 `prompts/memory.md`。
- 整理上下文时有必须保留的信息，才写 `prompts/compaction.md`。
- `memory/` 初始模板很少需要；需要时文件要小，扩展名 `.md` / `.txt` / `.yaml`。
