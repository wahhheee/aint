# 创作 AINT 作品

AINT 以"作品"为单位运行 AI 互动小说。作品是一个纯文本目录：Markdown、YAML、Liquid 模板、CSS，加上图片、音频与字体，没有可执行代码。玩家导入作品、配置自己的模型即可游玩。

分清三个读者：

- **你**：创作者，把用户的想法做成作品文件。
- **执笔者**：游玩时写正文的模型。它读到平台提示词，以及你写的执笔指令、开场、设定索引、命令表、状态说明与标签说明；用工具查资料、维护记忆与状态、给出选项。你写的每个文件，最终都是写给它读的。
- **玩家**：在阅读页里读正文、做选择、输入行动，看到 README、面板、命令与选项按钮。

平台已经给执笔者一套通用帮助（正文与工具的边界、沉浸、记忆、篇幅、交还选择），并按作品实际用到的功能裁剪：没有状态就没有状态说明与状态工具，没有命令就没有命令表。作品只需要写这部作品独有的东西。

## 立场

作品属于用户。题材、风格、口味与浓度都由用户决定，你的工作是把它完整、准确、高水准地做出来：用户描述的就是作品本来的样子，照它应有的样子写足。用户只给了一句话时，由你补全其余部分，补全的方向与用户已经给出的气质一致。

## 工作流程

### 1. 准备

- 找到命令行工具：PATH 中的 `aint`（Windows 为 `aint.exe`），或 AINT 发布包解压目录里的可执行文件；在 AINT 源码仓库中可以用 `go run ./cmd/aint`。找不到时照常创作，交付前按 [格式参考](references/format.md) 逐项自查。
- 创作只用 `aint work` 子命令：`validate <目录>`、`prompt <目录>`、`pack <目录> -o <zip>`（zip 放在作品目录之外）；`aint help` 显示用法。不带子命令运行 `aint` 会启动服务，并在可执行文件旁创建数据目录，创作时用不到。`aint work init` 只生成占位模板，直接写文件即可。
- 作品目录默认建在当前工作目录下，以作品 slug 命名；用户指定了位置时按用户的。
- 按需阅读：写文件前读 [格式参考](references/format.md)；写执笔指令、开场与设定前读 [写作](references/writing.md)；设计状态、命令、面板、标签与素材前读 [设计](references/design.md)。
- AINT 自带的示例作品可用于查阅格式用法；作品结构与写法依题材和需求组织。

### 2. 理解需求

从用户的描述与图片中整理出：

- **核心体验**：一句话说清玩家会得到什么。之后每个取舍都以它为准。
- **世界与人物**：舞台、主要人物、玩家扮演谁或以什么身份参与。
- **文风与审美**：人称、时态、笔调、节奏、描写的重心，用户的偏好与癖好。
- **走向**：主线与关键转折、结局方式，或完全开放。
- **玩法**：数值、检定、特殊输入、视角切换、读者干预、多个起点……体验需要时才引入。
- **参考图片**：分清是审美参考（转写成文风、配色与设定），还是要放进作品的素材（人物、场景、封面）。用户没说明时按审美参考处理；适合放进作品的，在第 3 步提一句。

用户没说的部分，依核心体验推断补全。用户说"不要"的东西，照实记进你自己的需求笔记，并分清是偏好（更喜欢别的）还是排除（明确不接受）：偏好在作品里只写它的正面形式，排除在作品里直接写明（见写作原则 4）。需求笔记放在作品目录之外：作品目录里的文件都会被打包分发，设定文档还会被执笔者读到。

### 3. 对齐

动手前给用户一份简短的设计概要（核心体验、玩家身份、文风方向、打算用到的功能），把需要用户拍板的事集中在一轮里问清：

- 会根本改变作品形态、又无法从描述推断的分歧（例如玩家扮演主角还是作为读者旁观；用户没指定、几种人称都说得通时的人称）；
- 你替用户补全的核心设定（凶手与真相、人物的隐藏身份、结局方式），各用一句话点出，让用户可以否决；
- 用户的"不要"分不清是偏好还是排除、又会影响作品时，写出你的理解请用户确认；
- 默认关闭、但开启后能明显改善这部作品体验的功能（见下方"开关"），附一句理由与你的推荐。

其余细节由你决定，交付时说明。用户看过概要后回复"按你的推荐来"，就是同意了概要中推荐开启的功能，照推荐开启。用户跳过对齐、要求直接做时，按推荐默认完成：默认关闭的功能保持关闭，把建议开启的功能放在交付说明里。

### 4. 设计

从最小可玩的作品出发：`work.yaml` + 执笔指令 + 开场就能玩。再逐项判断设定文档、状态、命令、样式标签、面板、主题、素材是否服务于核心体验，需要才加。没用到的功能不花 token，也不会出现在执笔者的提示词里；用不上的功能只会增加执笔者的负担。需求与原语的对应见 [设计](references/design.md) 第 1 节。

### 5. 写作

建议顺序：执笔指令 → 开场 → 设定 → 状态 / 命令 / 标签 / 面板 → 主题与素材 → `work.yaml` → `README.md`。执笔指令与开场最值得花心思：前者决定执笔者是一个怎样的人，后者是执笔者模仿的第一份正文。写法见 [写作](references/writing.md)。

### 6. 校验与通读

```bash
aint work validate <作品目录>
aint work prompt <作品目录> [--opening <开场ID>] [--vision]
```

- `validate`：错误清零，警告逐条处理（`W-NO-DESC` 补说明，`W-UNKNOWN-FIELD` 多半是拼写错误）。它检查结构、引用与 Liquid 语法，不检查过滤器名、状态字段名、正文里的标签与路径，也不渲染静态开场与面板；这些逐项自查，见 [格式参考](references/format.md)"校验覆盖"一节。
- `prompt`：打印执笔者实际收到的完整提示词，执笔指令在这里以初始状态渲染（模板出错会直接报错）；生成式开场的指引附在开场消息里，静态开场的正文不在其中。把自己当作执笔者读一遍：嗓音是否一致，读完是否知道第一段该怎么写，有没有与平台提示词重复或冲突的地方，标签、命令、状态的说明是否准确。多开场时逐个开场看。
- 条件允许时在 AINT 中把作品目录导入为开发目录试玩几个回合，看静态开场与面板的实际样子，打开阅读页的调试开关看执笔者读了什么、怎样使用工具。做不到时，在交付说明里请用户导入后看一眼开场与面板。

### 7. 交付

告诉用户：作品目录、文件一览、你替用户做的主要决定、建议开启但未开启的功能、没能验证的部分（静态开场与面板的实际显示、未核实的史实与专业知识）。导入方式：

- 书架 →「导入作品」→「开发目录」，填作品目录的路径：保存文件后自动重新校验并更新，适合边玩边改；
- 或 `aint work pack <作品目录> -o <文件>.zip` 打包，分享或在书架上导入。

### 修改已有作品

先读完全部文件再动手。保持作品 ID、开场 ID、文档 ID、状态字段名稳定，已有存档依赖它们。已经发布给玩家的作品改版时递增 `version`，在 `changelog` 写本版变化；新增的状态字段给默认值。用户反馈"写得不对"时，先把反馈翻译成具体的目标写法，再判断该改执笔指令、开场还是设定；文风问题通常先看开场。

## 开关

`work.yaml` 中显式写出全部 `features` 与 `presentation` 开关，让用户一眼看到每个开关的状态。默认关闭的功能保持关闭，用户明确需要才开启；能明显改善这部作品体验的，在第 3 步询问用户。

| 开关 | 默认 | 适合询问开启的情形 |
| --- | --- | --- |
| `features.force_choices` | `false` | 以选项推进为主的作品：正文结束却没给选项时，平台追加一次提示让执笔者补上选项 |
| `features.dice` | `false` | 需要运气、检定、跑团味道的作品 |
| `features.timed_choices` | `false` | 有追逐、倒计时等紧迫情境的作品 |
| `presentation.text_effects` | `false` | 确有停顿、旁白式演出的作品（`<pause>`、`<fx>`、`<aside>`），用法限定在固定场合 |
| `presentation.dialogue` | `plain` | 只在用户明确要求说话人名字、颜色等视觉小说式样式时设为 `tagged` |

`features.free_input`、`features.ooc`、`presentation.stage` 默认开启，保持开启。常驻图片（`pin`）、`load: always` 的文档每回合都会发送，按需使用。

## 写作原则

详见 [写作](references/writing.md)，这里是要点：

1. **引导优于限制**：写"希望怎样"，把文风、审美与偏好上的每条禁止都改写成具体的目标写法；关键边界见第 6 条。
2. **让执笔者真心喜爱**：执笔指令要让执笔者成为由衷喜欢这部作品的文风、人物、审美与偏好的人，写出认同、欣赏与热爱。
3. **指令的文笔就是示范**：执笔指令本身的笔调符合作品要求的文风；执笔者会模仿它读到的文字。
4. **分清偏好与排除**：用户只是更喜欢别的，被比下去的那一样不点名写进作品，用对所好的正面描写占据它的位置；用户明确不接受的，直接点名写明作品里没有它，语气坚决，同时写出替代它的东西。
5. **少用模板与示例**：描述质感与原则，不给可以照抄的句子；执笔者会反复套用示例。开场例外，开场就是范文，按期望的正文认真写。
6. **强硬语气用在关键边界上**：用户明确不接受的内容，以及会破坏沉浸、让人出戏、毁掉体验的事，用坚决的说法，简短说一次；其余保持平和、欣赏的语气。
7. **不重复平台**：工具、选项按钮、记忆、篇幅、正文与工具的边界由平台提示词负责，作品只写独有的内容。

## 易错点

- **面板**：单行、少量内容，照顾手机。顶栏至多一个面板，输出一句短话；侧栏与抽屉每项一行，累积的列表只显示最近几条或允许滚动；不做多层标题的仪表盘。见 [设计](references/design.md) 第 3 节。
- **渲染检查**：校验后核对过滤器名、状态字段名、开场标签与执笔指令中的路径，并检查实际显示。
- **ID 与路径**：`[[id]]` 只在执笔者读取设定文档时补全为路径；执笔指令、`always` 文档、命令模板里希望执笔者去读的文件写完整路径 `/work/lore/…`；素材、人物、命令各有自己的写法。见 [格式参考](references/format.md)"ID 与路径"一节。
- **选项的 `command`**：只在选中后需要执行作品命令时才填，普通行动选项只要 `id` 与 `label`。执笔者给出的选项与静态开场的初始选项规则相同。
- **开场**：按期望的正文写到最好，它是执笔者模仿的第一份正文。
- **说话人样式**：没有明确要求时保持 `plain`；`tagged` 会把对白固定成一种写法，与灵活多变的现代文文风冲突。
- **样式标签与文字特效**：只用在不需要文笔的固定内容上（判决、技能名的呼喊、提示信息、特殊演出），每个标签写清唯一的使用场合。模型会积极使用标记语言，标记内的文字也容易写得死板；需要文笔的描写始终留在正文里。
- **命令**：模板写成叙述层面已经成立的事实与下一段的起点（例如这一段跟随谁），不断言场景里此刻的状态；并在执笔指令中约定命令带来的变化直接体现在正文里。见 [写作](references/writing.md) 第 10 节；视角切换见 [设计](references/design.md) 第 5 节。
- **体验类功能**：`force_choices` 等用户没提到的功能，按"开关"一节询问。

## 交付前检查

- [ ] `aint work validate` 没有错误，警告已处理或有理由保留
- [ ] 校验不覆盖的部分已自查：过滤器名、`state.…` 字段名、开场里的标签、执笔指令与模板里的 `/work/…` 路径
- [ ] `aint work prompt` 读下来嗓音一致，没有与平台重复、冲突或互相矛盾的说法
- [ ] 执笔指令以正向引导为主，笔调符合作品文风，写出了对作品的喜爱
- [ ] 用户的偏好只以正面形式出现；用户明确排除的内容写明了范围与替代，设定、开场、人物档案与选项里都没有它
- [ ] 每个静态开场都达到期望的正文水准；生成式开场的指引清楚
- [ ] `features` 与 `presentation` 显式写出，默认关闭的功能没有擅自开启
- [ ] 样式标签与特效只用在固定场合，说明写清唯一的使用场合
- [ ] 面板轻量，手机上可读
- [ ] 命令模板不会引出确认、复述或预告式的回应
- [ ] 状态字段都有 `desc`，写清含义、范围与更新时机
- [ ] 素材的 `description` 具体，背景图标了 `role: background`
- [ ] `README.md` 向玩家介绍作品与玩法
